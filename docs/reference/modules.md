# Módulos — Paperfolio

> Dónde vive cada cosa en el código y qué es responsable de qué.

| Módulo | Responsable de |
|---|---|
| `src/lib/site.ts` | Datos del sitio (`siteConfig`: nombre y descripción) para la metadata y la UI |
| `src/lib/cn.ts` | `cn()`: une clases y descarta las vacías (clases condicionales). No resuelve conflictos de Tailwind (`px-4` y `px-0` quedan las dos) |
| `src/lib/share.ts` | `shareOrCopy()` (Web Share API con caída a copiar el link) y `copyText()` (Clipboard API); no lanzan, devuelven el resultado para que la UI avise |
| `src/lib/gsap.ts` | Registra `ScrollTrigger` y exporta `gsap` y `MOTION_OK` (la consulta de reduced-motion para `gsap.matchMedia`); solo para componentes de cliente |
| `src/lib/env.ts` | Valida con Zod las variables del servidor (`MONGODB_URI`, `MONGODB_DB`; `IP_HASH_SAL` aparte con `leerIpHashSal()`, `RESEND_API_KEY` con `CONTACTO_EMAIL_DESTINO` con `leerEmailConfig()`, y `GMAIL_USER` con `GMAIL_APP_PASSWORD` con `leerGmailConfig()` (la contraseña sin espacios, de 16 caracteres), para que la base no las exija) y las expone tipadas (`env`, `leerEnv()`). Los errores nombran la variable, nunca el valor |
| `src/lib/db.ts` | `conectar()`: conexión de Mongoose cacheada en `globalThis`; `desconectar()` la cierra (para tests). Nunca loguea la URI |
| `src/models/Consulta.ts` | Modelo Mongoose de la colección `consultas` (ver [domain.md](domain.md)) |
| `src/app/api/consultas/route.ts` | `POST /api/consultas`: lee la IP, llama a `crearConsulta` y traduce el resultado a HTTP |
| `src/lib/api-error.ts` | `respuestaError(status, codigo, mensaje, extra?)` y `respuestaConfiguracionInvalida()`: el formato único de error de la API (`/api/salud` y `/api/consultas`) |
| `src/lib/ip.ts` | `leerIp(headers)`: primer valor de `x-forwarded-for` o `x-real-ip`; vacío si no hay |
| `src/lib/consultas.ts` | `crearConsulta(input, { ip, avisar? })`: valida con `parseContactRequest`, descarta si el campo trampa `sitio_web` trae algo (antes de validar), corta con `limite` al llegar a 5 consultas por hora del mismo `ipHash` y guarda (si no puede crear los índices de `consultas`, loguea el nombre del error y guarda igual). Devuelve `creada`, `invalida` (errores por campo), `limite` o `descartada`; lanza un error si la `ip` viene vacía. Tras guardar llama a `avisar(consulta)` (por defecto `avisarConsultaNueva`): si sale bien marca `emailEnviado: true`; si falla, la consulta queda con `emailEnviado: false`, se loguea solo el nombre del error y igual devuelve `creada` |
| `src/lib/bandeja.ts` | `parsearFiltros(searchParams)` valida con Zod (lo inválido se descarta; ceros a la izquierda en `pagina` no cuentan) y `listarConsultas({ tipo?, estado?, pagina })` recibe esos filtros ya validados (la página fuera de rango devuelve la última válida, mínimo 1). Devuelve `{ items, total, paginas, pagina }` de a 20, con campos explícitos (`id`, `nombre`, `tipo`, `estado`, `extracto`, `creadaEn`): `ipHash` y `email` no salen de ahí. Crea los índices de `consultas` (`asegurarIndicesDe`; si falla, loguea el nombre del error y sigue). Un estado guardado desconocido o ausente sale como `nueva` (`estadoLeido`) |
| `src/lib/estados-consulta.ts` | Módulo puro (sin base; lo usan el modelo, la bandeja y el cliente): `ESTADOS_CONSULTA`, `ETIQUETAS_ESTADO`, `TRANSICIONES`, `origenesDe(estado)`, `esEstadoConsulta`, `estadoLeido(valor)` (desconocido o ausente → `nueva`), `filtroDeEstados(estados)` (la condición de Mongo coherente con `estadoLeido`) `LARGO_MAXIMO_NOTA` (2000, para el formulario y el servidor), `ESTADOS_PARA_RESPONDER` (solo `en_curso`, #40) y `LARGO_MAXIMO_RESPUESTA` (5000). Los componentes importan de acá, no de `bandeja.ts` (que arrastra Mongoose) |
| `src/lib/seguimiento.ts` | `obtenerConsulta(id)`: el detalle para el panel (con el `email`, sin `ipHash`) y el historial con el nombre de cada autor; `null` si el id no es un ObjectId de 24 hex o no existe. `cambiarEstado(id, estado, autor)` y `agregarNota(id, texto, autor)` validan con Zod y escriben con un solo `updateOne` (estado + entrada en el seguimiento); devuelven `{ ok: true }` o `{ ok: false, error: "no-encontrada" \| "transicion-invalida" \| "invalida", mensaje }` y lanzan si el `autor` no es un id (sale de la sesión). `reservarRespuesta(id, texto, autor)` y `completarRespuesta(id, autor, fecha, emailEnviado)` (las usa `respuestas.ts`): reservar agrega, con un `updateOne` condicionado a `en_curso` y a que no haya otra pendiente sin vencer (`RESERVA_VENCE_MS`, 2 min), la entrada `respuesta` sin `emailEnviado`, y devuelve su `fecha` o `estado-invalido`, `en-envio` o `no-encontrada`; completar, si el email salió y sigue en curso, en un solo `updateOne` (pipeline) marca `emailEnviado: true`, agrega la entrada `estado` y la pasa a `respondida`; si no, solo marca `emailEnviado` en esa entrada (`arrayFilters`); devuelve `completada`, `sin-entrada` (la entrada ya no estaba pendiente) o `sin-consulta`. Exporta `ID_VALIDO`, `exigirAutor` y `NO_ENCONTRADA` |
| `src/lib/respuestas.ts` | `responderConsulta(id, texto, autor, transporte?, opciones?)` (#40): valida el texto (1 a 5000, CRLF como LF), exige que la consulta esté `en_curso` y la responde por SMTP de Gmail (`nodemailer` 10, importado con el alias npm `nodemailer-10`; `leerGmailConfig()`), desde `GMAIL_USER` al email **guardado en la consulta** (validado de nuevo), con asunto `Re: tu consulta en Paperfolio (<tipo>)` (la etiqueta del tipo, por ejemplo "Cotización de proyecto") y texto plano: la respuesta y, debajo, el mensaje original citado. El nombre y el tipo se limpian de caracteres de control. Espera hasta 10 s (nodemailer no se puede cancelar: sus timeouts propios son más cortos, y si igual vence, el mensaje avisa que el email puede llegar). Reserva la respuesta antes de enviar (`reservarRespuesta`: un segundo intento simultáneo recibe `en-envio`) y la completa al terminar (`completarRespuesta`); sin la configuración de Gmail o con un destino guardado inválido no intenta ni registra nada. Devuelve `{ ok: true, estadoCambiado }` o `{ ok: false, error: "invalida" \| "no-encontrada" \| "estado-invalido" \| "en-envio" \| "envio-fallido" \| "registro-fallido", mensaje }` (`registro-fallido`: el envío terminó pero no se pudo registrar, y la entrada queda sin confirmar; tras un `timeout` la entrada queda sin confirmar, para que la reserva bloquee otro envío, y se completa cuando el envío termina con la tarea que recibe `opciones.seguir`, que la acción le pasa a `after`); en `envio-fallido` el mensaje lleva solo el código del error (`EAUTH`, `ETIMEDOUT`, `timeout`, `configuracion`, `destino-invalido`…), que es lo único que se loguea. El transporte se inyecta en los tests |
| `src/app/panel/consultas/[id]/` | Detalle de una consulta: `page.tsx` (Suspense), `detalle.tsx` (`requerirRol` y después `obtenerConsulta`; 404 si no existe), `controles.tsx` (cliente, `useActionState`; si guardar la nota falla, el texto vuelve en el estado de la acción para no perderlo con el reset del formulario), `acciones.ts` (server actions `cambiarEstadoAccion`, `agregarNotaAccion` y `responderAccion`, con `requerirRol` cada una y el autor de la sesión; refrescan si salió bien o si la transición fue inválida, y `responderAccion` también si el envío falló o la consulta ya no estaba en curso). El formulario "Responder por email" solo aparece en curso, pide confirmación y, si falla, conserva el texto |
| `src/lib/proyecto-entrada.ts` | Módulo puro (sin Mongoose; lo usan el servicio, las acciones y el formulario): `proyectoEntradaEsquema` (extiende `proyectoEsquema`, así no se guarda nada que la lectura descarte, como un string vacío en el stack; suma los largos de `LIMITES` y `publicado`), `sugerirSlug(nombre)`, `datosDeFormulario(formData)` (listas por línea, sin las vacías), `valoresDeFormulario`, `valoresDeProyecto` y `erroresPorCampo(issues)` (un mensaje en castellano por campo, `caso.problema` incluido) |
| `src/lib/proyectos-admin.ts` | CRUD de proyectos del panel (#51), sin chequeo de rol (lo hacen las acciones) ni next/cache: `listarProyectosAdmin()` (todos, en orden, con la cantidad de demos), `obtenerProyectoAdmin(id)` (con `version`, la key del formulario), `crearProyecto(datos)` (al final del orden), `actualizarProyecto(id, datos)` (sin `imagen`, la quita), `borrarProyecto(id)` (el proyecto y después todas sus demos; si fallan las demos, `ok` con un `aviso` que la lista muestra; la imagen de Blob queda), `publicarProyecto(id, publicado)` y `reordenar(ids)` (todos los ids, cada uno una vez; si la lista no coincide con la base, `desactualizada` y no cambia nada). Validan con `proyectoEntradaEsquema` antes de escribir; el slug duplicado lo frena el índice único (`asegurarIndicesDe`). Devuelven `{ ok: true, id?, aviso? }` o `{ ok: false, error: "invalida" \| "no-encontrado" \| "desactualizada", mensaje, campos? }` |
| `src/app/panel/proyectos/` | Sección de proyectos del panel (solo `admin`): `page.tsx` (lista), `nuevo/page.tsx` y `[id]/` (`page.tsx` con Suspense y `editar.tsx`), cada una con `requerirRol(…, "admin")` antes de leer; `lista.tsx` y `formulario.tsx` (cliente, `useActionState`; la imagen se sube por `fetch` a `/api/imagenes`; un envío fallido remonta los campos con lo mandado); `acciones.ts` (server actions con `requerirRol` cada una; si escriben, `updateTag(TAG_CONTENIDO)` y vuelven a la lista o la refrescan) |
